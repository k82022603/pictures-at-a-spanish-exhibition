## 1. 이 곡에는 녹음이 없다

먼저 이것부터 짚어야 나머지가 이해됩니다.

**보통 음악은 이렇게 만듭니다.**

```
연주자가 악기를 연주한다 → 마이크가 공기 진동을 받는다 → 파일로 저장한다
```

**이 곡은 이렇게 만듭니다.**

```
컴퓨터가 「피아노 소리란 이런 파형이다」를 계산한다 → 파일로 저장한다
```

**연주자도 없고 마이크도 없고 악기도 없습니다.** 피아노 소리도 계산으로 만들고, 오르간도 기타도 드럼도 전부 계산으로 만듭니다. 그 이유와 판단 근거는 [06. 음악 제작 방식 결정서](<06. 음악 제작 방식 결정서.md>)에 있습니다.

> **그래서 「샘플을 하나도 안 썼으므로 권리가 전부 이 프로젝트에 있다」**는 말이 성립합니다. 남의 녹음을 한 조각도 안 가져왔습니다.

## 2. 렌더 — 악보를 소리로 「굽는」 것

### 2.1 한 줄로

> **렌더 = 악보에 적힌 숫자를 실제 소리의 파형으로 계산해내는 일.**

「출력한다」에 가깝고, 이 프로젝트에서는 **「굽는다」**고 말해 왔습니다.

### 2.2 무엇을 계산하는가

**소리는 공기의 떨림입니다.** 그리고 컴퓨터는 그 떨림을 **1초에 44,100번 숫자로 적어** 저장합니다. 이 숫자 하나하나를 **표본**이라고 부릅니다.

**그러니까 「도를 0.3초 동안」이라는 악보 한 줄이 실제로는 이런 뜻입니다.**

| 악보에 적힌 것 | 실제로 필요한 것 |
|---|---|
| `64번 음 · 0.3초 · 세기 0.8` | **숫자 13,230개** (0.3초 × 44,100) |

**전곡 9분 40초면** — 580초 × 44,100 × 좌우 2채널 = **약 5,116만 개의 숫자**입니다.

**렌더는 이 5,116만 개를 전부 계산해내는 일입니다.** 그래서 이 PC에서 **3~5분** 걸립니다.

> **「긴 렌더는 시간을 알려주고 시작한다」는 규칙이 있는 이유입니다.** 3~5분간 아무 응답이 없습니다.

### 2.3 무엇이 계산되는가 — 피아노 한 음을 예로

피아노 소리 하나를 만들려면 이것들을 다 계산합니다.

| 무엇 | 왜 |
|---|---|
| 기본음 + 배음 여러 개 | 피아노는 한 음이 아니라 여러 진동이 겹친 소리다 |
| **현의 비조화도** | 진짜 현은 배음이 정확히 2배·3배가 아니라 조금씩 위로 어긋난다. 이게 없으면 「전자 오르간」처럼 들린다 |
| **이중 감쇠** | 처음엔 빨리 줄다가 나중엔 천천히 준다 |
| 해머 잡음 | 망치가 현을 때리는 「퍽」 |
| 방 울림 | 피아노가 놓인 공간 |

**이걸 음 하나마다 합니다.** 전곡에 음이 수만 개 있습니다.

### 2.4 그래서 「음 하나 고쳤는데 왜 3분 걸리나」

**한 음만 다시 계산할 수가 없습니다.** 소리는 서로 겹쳐서 섞이기 때문에, 하나를 바꾸면 그 뒤로 겹치는 것들이 전부 달라집니다. 그래서 **전곡을 처음부터 다시 계산**합니다.

> **「렌더 4회」라고 적혀 있으면 곡 전체를 네 번 새로 만들었다는 뜻입니다.**

### 2.5 같은 코드는 같은 소리를 낸다 (BL-30)

**이게 당연해 보이지만 넉 달 동안 아니었습니다.**

소리에 「연주 흔들림」을 주려고 난수(무작위 숫자)를 쓰는데, **씨앗을 안 정하면 돌릴 때마다 다른 숫자가 나옵니다.** 그래서 같은 코드를 두 번 렌더하면 다른 소리가 났습니다.

지금은 씨앗을 고정해서 **같은 코드 → 100% 똑같은 파일**입니다. 이게 있어야 **「내가 고친 것 때문에 바뀐 것인가, 난수가 달라져서 바뀐 것인가」**를 가를 수 있습니다.

## 3. 소리가 파일이 되기까지 — 전체 경로

```
① 전곡화성.py      악보 + 악기 설계도 (사람이 읽는 코드)
        ↓  렌더 (3~5분)
② 성부별 소리      피아노·오르간·베이스·기타·무그·현악·타악·드럼 — 여덟 갈래
        ↓  스템으로 저장                     ← 32비트 실수, 손실 없음
③ 스템/ 폴더       악기별 트랙 여덟 개
        ↓  믹스 (음량·좌우·울림을 정한다)
④ 마스터           전곡 한 덩어리                ← ★ 여기가 오늘 고친 곳
        ↓  납품용으로 굽는다
⑤ FLAC · MP3      들으실 파일
```

**용어 셋만 풀어둡니다.**

| 말 | 뜻 |
|---|---|
| **스템 (stem)** | **악기별 트랙.** 피아노만 담긴 파일, 베이스만 담긴 파일… 여덟 개. 나중에 「피아노만 줄이자」가 가능해진다 |
| **믹스 (mix)** | 여덟 갈래를 하나로 합치면서 **음량·좌우 위치·울림**을 정하는 일 |
| **마스터** | 믹스가 끝난 **전곡 한 덩어리 파일** |

> **스템을 따로 두는 것이 왜 중요한가** — 스템이 있으면 **렌더를 다시 안 하고 믹스만** 다시 할 수 있습니다. **3~5분이 20초**가 됩니다. 「무그를 조금 키워볼까」를 스무 번 시험할 수 있게 됩니다.

## 4. 비트depth — 숫자를 얼마나 정밀하게 적는가

### 4.1 무엇인가

**2.2절에서 「1초에 44,100번 숫자를 적는다」고 했습니다.** 그럼 **그 숫자 하나를 얼마나 촘촘하게 적을 것인가**가 남습니다.

> **비유 — 자로 길이를 잰다고 생각해 보세요.**
> 눈금이 **1mm**인 자와 **0.001mm**인 자가 있습니다. 같은 물건을 재도 적히는 값이 다릅니다.
> **비트depth가 그 눈금의 촘촘함입니다.**

| | 눈금이 몇 칸인가 | |
|---|---|---|
| **16비트** | **65,536칸** | CD가 이것 |
| **24비트** | **1,677만 칸** | 녹음실 표준 |
| **32비트 실수** | **사실상 무제한** | 계산 중에 쓰는 것 |

### 4.2 「양자화」 — 눈금에 맞춰 떨어뜨리는 일

계산으로 나온 값이 예를 들어 **0.3729481…** 이라고 합시다. 16비트 눈금에 맞추려면 **가장 가까운 칸으로 옮겨야** 합니다. 그때 **버려지는 나머지**가 생깁니다.

**이 버려지는 나머지를 「양자화 오차」라고 부르고, 실제로는 아주 작은 잡음으로 들립니다.**

**16비트의 잡음은 −96 dB 근처입니다.** 이 곡에서 가장 조용한 6악장이 −22.6 dB이므로, **잡음은 그보다 70 dB 이상 아래**입니다. **사람 귀에 안 들립니다.**

## 5. 오늘 찾은 것 — 마지막 한 단계에서만 떨어뜨리고 있었다

### 5.1 발견

**검수자 질문** — *"FLAC 24bit인가?"*

**아니었습니다. 16비트였습니다.** 그런데 **FLAC 탓이 아니었습니다.**

3절의 경로를 다시 보면 —

| 단계 | 정밀도 |
|---|---|
| ② 계산 중 | **32비트 실수** |
| ③ 스템 저장 | **32비트 실수** — 손실 없음 |
| **④ 마스터** | **16비트** ← **여기서만 떨어뜨리고 있었다** |
| ⑤ FLAC | 16비트 (④를 그대로 담았을 뿐) |

**FLAC은 무손실입니다.** 16비트짜리를 줬으니 16비트로 담은 것뿐입니다.

**원인이 코드 한 줄이었습니다.**

```python
(np.clip(stereo, -1, 1) * 32767).astype(np.int16)
```

### 5.2 덤으로 나온 결함 — 「잘라내기」와 「반올림」

위 줄에 문제가 하나 더 있었습니다.

**`.astype(np.int16)`은 반올림이 아니라 0 쪽으로 잘라냅니다.**

| 계산값 | **반올림하면** | **잘라내면** |
|---|---|---|
| 3.7 | **4** | **3** |
| 3.2 | 3 | 3 |
| −3.7 | **−4** | **−3** |

**왜 이게 나쁜가** — 잘라내면 **오차가 항상 0 쪽으로만 쏠립니다.** 반올림은 위아래로 반반씩 흩어집니다.

> **저울이 항상 아래로만 깎는다고 생각해 보세요.** 열 번 재면 열 번 다 가볍게 나옵니다. 오차가 **한쪽으로 쌓입니다.**
>
> 소리에서는 이것이 **「신호와 상관을 갖는 오차」**가 됩니다. 같은 크기의 무작위 잡음보다 귀에 걸리기 쉽습니다.

**아주 작은 차이지만 공짜로 고칠 수 있는 것**이었습니다.

### 5.3 고친 것 — 24비트보다 더 위로 갔다

**검수자** — *"24bit 올릴 방법은? 더 높여도 좋고"*

**32비트 실수로 갔습니다.** 이유가 있습니다.

> **믹스가 원래 32비트 실수입니다.** 그러니 **그대로 쓰면 버리는 것이 아예 0**입니다. 24비트 정수로 가면 그래도 조금은 떨어뜨려야 합니다.

**그리고 이 방식에서는 5.2절의 문제도 같이 사라집니다** — 눈금에 맞출 일이 없으니 잘라낼 일도 없습니다.

| | 형식 | 왜 |
|---|---|---|
| **마스터 WAV** | **32비트 실수** | **양자화가 아예 없다** |
| **납품 FLAC** | ~~**24비트**~~ → **★ 32비트 (확정)** | ~~FLAC은 실수를 못 담는다. 24비트가 최선~~ |
| 납품 MP3 | 320 kbps | 종전대로. 호환성용 |

> **⚠ 「24비트가 최선」이 틀렸다 — 별첨에서 32비트로 갔다.**
> **FLAC 이 실수를 못 담는 것은 맞다.** 그러나 **정수 32비트는 담을 수 있고**, 못 한 것은 FLAC 이 아니라 **ffmpeg 의 인코더**였다(24비트가 상한이고 옵션을 무시한다). 공식 FLAC 도구를 깔아서 됐다. **경위와 실측은 별첨.**

### 5.4 소리가 바뀌었나 — 안 바뀌었다

**승인하신 16비트 판과 새 32비트 판을 대조했습니다.** 새 판을 16비트로 되돌려 승인본과 표본 하나하나 비교했습니다.

| | |
|---|---|
| 표본 수 | 5,115만 6천 개 |
| 다른 표본 | 2,548만 9천 개 (49.8%) |
| **최대 차이** | **1칸** (16비트 눈금 하나) |
| **차이의 크기** | **−93.3 dB** |

**절반이 다르지만 전부 「눈금 한 칸」 차이입니다.** 이게 정확히 **잘라내기를 반올림으로 바꿨을 때 나오는 모양**입니다.

> **−93.3 dB는 안 들립니다.** 이 곡에서 가장 조용한 자리보다 70 dB 아래입니다.
>
> **즉 오늘 바뀐 것은 파일 형식이지 음악이 아닙니다.**

## 6. 지금 쓰는 형식과 크기

| 무엇 | 형식 | 전곡 크기 | 손실 |
|---|---|---|---|
| 마스터 | 32비트 실수 WAV · 44.1 kHz | **195 MB** | **없음** |
| 납품 | **32비트 FLAC** (★ 확정) | **141 MB** | **없음** |
| 납품 | MP3 320 kbps | **22 MB** | 아래 7절 |

**FLAC은 압축돼 있는데도 무손실입니다.** ZIP처럼 되돌리면 원본과 한 비트도 안 다릅니다 — 실제로 확인했습니다.

**MP3는 다릅니다. 소리를 실제로 버립니다.**

## 7. MP3 320kbps는 무엇을 버리나

**이 값도 근거가 문서 어디에도 없었습니다.** v1.4 때 「MP3에서 낼 수 있는 최고」라서 쓴 뒤 관성이었습니다. 재봤습니다.

| | |
|---|---|
| 버려진 소리의 크기 | **−56.5 dB** |
| 신호 대 오차 | **38.9 dB** |

**그리고 버리는 양이 구간마다 다릅니다.**

| 구간 | 신호 대 오차 | |
|---|---|---|
| 6악장 (가장 조용) | 50.4 dB | 거의 안 버린다 |
| 7악장 (그녀) | 45.9 dB | |
| 9:26 해소 | 44.4 dB | |
| **9악장 정점** | **34.7 dB** | ← **가장 많이 버린다** |

**소리가 두꺼울수록 압축기가 더 많이 버립니다.** 하필 곡의 정점이 가장 두꺼운 자리입니다.

> **−56.5 dB가 안 들릴 만큼 작은가** — 대부분의 자리에서는 그렇습니다. 다만 **「음질을 판정하는 파일」로 MP3를 쓰는 것은 앞뒤가 안 맞습니다.** [08](<08. 중간 점검과 인수인계.md>) 1장이 MP3를 「음질 판정의 기준」이라고 부르고 있는데, **압축해서 버린 파일을 기준으로 삼고 있었던 셈**입니다.
>
> **그래서 오늘부터 FLAC을 함께 냅니다.** MP3는 호환성용으로 남깁니다.

## 8. 숫자 검증은 어느 파일로 하나

**항상 마스터(WAV)로 합니다. MP3로 재지 않습니다.**

그러므로 이 프로젝트가 쌓아온 실측값 — 경직됨 지표, 악장별 음량, 9:26의 F♯ 비중 — 은 **MP3의 손실과 무관합니다.**

**영향받는 것은 「귀로 듣는 판정」 하나뿐이고, 그게 이 프로젝트에서 제일 중요한 판정입니다.**

> **한 번 크게 데인 적이 있습니다** — 절대값을 **서로 다른 두 도구**로 재서 비교한 적이 있고, 7악장이 떨어진 줄 알았는데 같은 방법으로 재니 안 변했습니다. **재는 방법이 다르면 숫자를 비교하면 안 됩니다.**

## 8.5 소리의 크기 — LUFS 와 마스터링

**2026-08-23 추가.** 검수자 질문에서 나왔다 —

> *"WBS 1.5.2 「마스터링 (−14 LUFS)」 이것 뭐야? 어제 내가 놓친거야? 쉬운말로 설명해줘.
> 유튜브 말고 다른 곳에 올릴 때 문제가 발생할 수 있다? 음이 깍아야 한다는건가?"*

**먼저 결론 — 할 일이 없다. 그리고 놓치신 것도 아니다. 내가 걱정을 만들어 냈다.**

### 8.5.1 LUFS 가 뭔가 — 「소리의 체감 크기」

**여러 곡을 이어 들을 때 어떤 건 크고 어떤 건 작으면 볼륨을 계속 만지게 된다.**
그래서 유튜브·스포티파이 같은 데는 **올라온 곡을 자기들 기준으로 자동으로 맞춰 준다.**
그 기준이 대략 **−14** 다.

**LUFS 는 그 「체감 크기」를 재는 단위**다. 사람 귀가 실제로 크게 느끼는 대역에
가중치를 주고, **조용한 구간은 빼고** 센다.

### 8.5.2 재봤다 — 이미 맞다

| | |
|---|---|
| 목표 | −14 LUFS |
| **전곡 E 실측** | **−13.4 LUFS** |
| 가장 큰 순간 (True Peak) | **−1.5 dBTP** — 넘치면 소리가 깨지는데 여유가 있다 |
| 음량 폭 (LRA) | 4.7 LU |

```
ffmpeg -i <파일> -af loudnorm=I=-14:print_format=summary -f null -
```

**Suno 가 알아서 그 크기로 내줬다.** 우리가 마스터링 단계를 안 거쳤는데도 맞은 이유가 그것이다.

### 8.5.3 「음을 깎는 것」이 아니다

| | |
|---|---|
| 흔한 오해 | 소리를 눌러서 작게 만든다 |
| **실제** | **전체 크기를 목표에 맞추고, 최대치가 넘치지 않게 한다** |

**우리 곡은 둘 다 이미 통과했으므로 아무것도 안 깎는다.**

### 8.5.4 ★ 내가 왜 틀렸나 — 자를 안 재고 썼다

**어제 −16.7 dB 라는 숫자를 보고 「목표 −14 보다 작다」고 읽었다.**

**그 둘은 다른 자다.**

| | 무엇을 재나 | 전곡 E |
|---|---|---|
| **RMS** | 소리 에너지의 단순 평균. **귀를 고려 안 한다** | −16.7 dB |
| **LUFS** | **사람 귀 기준** 체감 크기. 조용한 구간은 뺀다 | **−13.4** |

**같은 소리인데 자가 달라 숫자가 다르다.** 나는 RMS 값을 LUFS 목표 옆에 나란히 놓고
비교했고, **그래서 「마스터링을 안 했다」는 걱정을 만들어 검수자에게 보고했다.**

> **어제부터 같은 모양을 네 번째 겪었다** — `악장표.py`(우리 악보 전제) ·
> `자막생성.py`(chordlog 전제) · `영상검증.py`(우리 곡과 견줌) · **여기(다른 자의 값을 나란히 놓음).**
>
> **앞의 셋은 도구가 조용히 틀린 것이었고, 이번엔 내가 두 자를 섞었다.**
> 공통점은 **「숫자가 나왔으니 맞겠지」** 다.

**규칙 — 두 숫자를 견주기 전에 「같은 자로 잰 것인가」를 먼저 묻는다.**

### 8.5.5 다른 데 올려도 되나

**된다.** 어제 내가 *"유튜브 말고 다른 곳에서 문제될 수 있다"* 고 한 것도 근거가 없었다.
**−13.4 는 어디에 올려도 맞는 크기다.**

**WBS 1.5.2 「마스터링(−14 LUFS)」은 「할 필요가 없어서 안 한 것」으로 닫는다.**

# 별첨 — 32비트 FLAC까지 갔다 (2026-08-12 저녁)

**검수자** — *"내가 원하는 것은 32bit FLAC 음원임."*

**됐습니다.** 그 과정에서 도구의 한계를 하나 만났고, 도구를 하나 더 깔았습니다.

---

## A1. ffmpeg 으로는 24비트가 끝이었다

본문 5.3절에서 24비트로 간 이유를 **「FLAC 은 실수를 못 담는다」**고만 적었는데 **그건 절반만 맞습니다.**

**진짜 이유는 도구였습니다.**

```
$ ffmpeg -h encoder=flac
    Supported sample formats: s16 s32
```

**s32 를 받는다고 적혀 있습니다.** 그래서 32비트가 되는 줄 알았는데, 실제로 구워 보면 이렇게 나옵니다.

| 넣은 것 | 나온 것 |
|---|---|
| `-sample_fmt s32` | **24비트** |
| `-sample_fmt s32 -bits_per_raw_sample 32` | **24비트** — 옵션이 무시된다 |

**ffmpeg 의 FLAC 인코더는 32비트 정수를 받아서 24비트로 깎아 씁니다.** 경고도 안 냅니다.

> **「지원 형식에 s32 가 있다」와 「32비트로 저장한다」는 다른 말이었습니다.** 확인 없이 넘어갔으면 **24비트짜리를 32비트라고 부르고 있었을 것**입니다. 이 프로젝트에서 여러 번 나온 「이름이 값과 다르다」의 또 한 사례입니다.

---

## A2. 공식 FLAC 도구를 깔았다

**FLAC 1.4 부터 32비트 정수를 정식 지원합니다.** 공식 도구를 깔면 됩니다.

```bash
winget install --id Xiph.FLAC
```

**설치된 것** — FLAC 1.5.0. `flac` · `metaflac` 두 명령이 생깁니다.

> **ffmpeg · gh · rclone 과 같은 방식입니다** (`CLAUDE.md` 4절). **winget 으로 깐 도구는 새 셸에서만 PATH 에 잡히므로**, 그 전에는 설치 경로를 직접 가리켜야 합니다.
>
> `%LocalAppData%\Microsoft\WinGet\Packages\Xiph.FLAC_*\flac-1.5.0-win\Win64\flac.exe`

---

## A3. 굽는 순서 — 한 단계가 더 필요하다

**FLAC 은 실수(float)를 못 담습니다.** 마스터가 32비트 실수이므로 **정수로 한 번 옮겨야** 합니다.

```
전곡화성.wav            32비트 실수      195 MB
        ↓  ffmpeg -c:a pcm_s32le
마스터32정수.wav        32비트 정수      195 MB
        ↓  flac --best
납품 FLAC               32비트 정수      141 MB
```

## A4. 무손실인지 확인했다

**구운 것을 다시 풀어서 원본과 표본 하나하나 대조했습니다.**

| | |
|---|---|
| 표본 수 | 5,115만 6천 개 |
| **결과** | **★ 비트 단위 100% 일치** |

**FLAC 은 압축돼 있는데도 되돌리면 한 비트도 안 다릅니다.** ZIP 과 같습니다.

## A5. 24비트와 무엇이 다른가 — 재봤다

**「32비트가 24비트보다 낫다」를 믿지 않고 쟀습니다.**

| | |
|---|---|
| 다른 표본 | 2,383만 개 / 5,116만 개 (**46.6%**) |
| 최대 차이 | **2칸** (24비트 눈금 기준) |
| **차이의 크기** | **−149.1 dB** |

### 이 숫자를 어떻게 읽어야 하나

**−149.1 dB 는 안 들립니다.** 비교하면 이렇습니다.

| | |
|---|---|
| 이 곡에서 가장 조용한 자리 (6악장) | **−22.6 dB** |
| 16비트의 잡음 바닥 | −96 dB |
| 24비트의 잡음 바닥 | −144 dB |
| **24비트판과 32비트판의 차이** | **−149.1 dB** |

> **24비트의 잡음 바닥보다도 아래입니다.** 즉 **24비트로 담아도 이미 이 음악이 가진 것을 전부 담고 있었습니다.**

### 그럼 32비트는 왜 하나

**두 가지 이유는 됩니다.**

**① 「마스터는 버리지 않는다」가 원칙으로 깔끔합니다.** 24비트도 충분하지만 **충분한 것과 안 버리는 것은 다릅니다.** 나중에 이 파일을 다시 처리할 일이 생기면(영상 붙이기·리마스터·보컬 얹기) **버린 적이 없는 파일에서 시작하는 편**이 낫습니다.

**② 앞으로 무엇을 더 할지 모릅니다.** 노랫말 보컬이 들어오고, 영상이 붙고, 최종 마스터링이 남아 있습니다. **매 단계가 조금씩 깎아내므로 시작점이 높을수록 여유가 있습니다.**

**하지만 정직하게 적어둡니다 — 지금 귀로 들어서 24비트와 32비트를 구별할 수 있는 사람은 없습니다.** 차이가 −149 dB 입니다.

## A7. ★ 확정 — 32비트로 굳혔다

> **검수자** — *"32bit로 굳혀줘."* (2026-08-12)

| | |
|---|---|
| **마스터** | **32비트 실수 WAV** — 양자화가 아예 없다 |
| **납품** | **32비트 FLAC** — 무손실 |
| 납품 (호환성) | MP3 320 kbps |
| ~~24비트~~ | 안 쓴다 |

### 문서에 적는 대신 도구로 만들었다

**이 프로젝트는 형식을 손으로 굽다가 두 번 틀렸다.**

| # | 무엇 | 얼마나 오래 |
|---|---|---|
| ① | `write_wav` 가 **마스터만 16비트로** 떨어뜨렸다 | 넉 달 |
| ② | `ffmpeg -sample_fmt s32` 가 **24비트를 썼다** | 오늘 하루 |

**둘 다 「이름이 값과 다르다」이고, 사람이 매번 확인할 일이 아니다.**

**`99. 작업 스크립트/납품.py` 를 만들었다.**

```bash
python 납품.py "산출물/20260812 - 한 마디" "full v4.15 9m40s"
```

**이 스크립트는 굽고 나서 반드시 되돌려 대조한다.** 무손실이 아니거나 32비트가 아니면 **오류로 멈춘다.** 그것이 이 도구의 존재 이유다.

```
FLAC     full v4.15 (32bit 마스터) 9m40s.flac  32비트  140.9 MB
MP3      full v4.15 (32bit 마스터) 9m40s.mp3  320k    22.1 MB

무손실 확인   ★ 비트 단위 100% 일치
비트depth     ★ 32비트
```

**`flac` 을 PATH 에서 못 찾으면 winget 설치 경로를 뒤진다** — winget 으로 깐 도구는 새 셸에서만 잡히기 때문이다(`CLAUDE.md` 4절).

### 대가를 정직하게 적는다

**24비트로도 충분했다.** 차이가 **−149.1 dB** 이고 24비트의 잡음 바닥(−144 dB)보다도 아래다. **지금 귀로 구별할 수 있는 사람은 없다.**

**그래도 32비트인 이유는 「충분한 것」과 「안 버리는 것」이 다르기 때문이다.** 뒤에 **보컬·영상·최종 마스터링**이 남아 있고 **매 단계가 조금씩 깎는다.**

**대가는 파일이 1.5배다** — 94 MB → 141 MB. Drive 용량과 전송 시간이 그만큼 는다.
