## 1. 왜 프로젝트 전체 버전인가

문서마다 따로 버전을 매기는 방식도 있지만 이 프로젝트에는 맞지 않는다. 문서들이 **같은 수치를 공유하기 때문**이다.

예를 들어 서사를 도입하면서 총 기간이 28일에서 28.5일로 바뀌었을 때, 세 문서를 동시에 고쳐야 했다.

- `00. 기획서` 7장 일정
- `01. 작업 분해 구조와 백로그` 요약·WBS·게이트 표
- `03. 스토리라인과 등장인물` 8장 제작 영향

문서별 버전이라면 "기획서 v1.2 + WBS v2.1 + 스토리 v1.0"이 서로 맞는 조합인지 매번 따져야 한다. **프로젝트 전체에 버전 하나를 붙이면 v0.6은 언제나 v0.6끼리 맞는다.** 되돌릴 때도 폴더 하나만 꺼내면 된다.

## 2. 버전 번호 규칙

`v[MAJOR].[MINOR]` 두 자리를 쓴다.

| 자리 | 올리는 시점 | 예 |
|---|---|---|
| **MAJOR** | 검수 게이트 통과 | G1 기획 승인 → **v1.0** / G2 데모 승인 → v2.0 |
| **MINOR** | 내용 추가·변경 | 서사 도입 → v0.4 / 버전 체계 도입 → v0.5 / 조성 변경 → v0.6 |

오탈자나 서식만 고친 경우는 버전을 올리지 않고 이력에 `(서식)`으로만 남긴다. 스냅샷도 만들지 않는다.

### 현재 위치

```
v0.1 → v0.2 → v0.3 → v0.4 → v0.5 → v0.6  ←  지금 (G1 승인 대기)
                                    │
                                    └─ G1 승인 시 v1.0
```

`v0.x`는 전부 **승인 전 초안**이다. G1을 통과하는 순간 v1.0이 되고, 그때부터 승인된 기준선이 생긴다.

### 스냅샷 소급 불가 안내

v0.1·v0.3·v0.4 시점의 파일은 **보관되어 있지 않다.** 버전 체계를 v0.5에서 도입했기 때문이다. 이 세 버전은 이력만 기록으로 남는다.

다만 v0.2는 예외다 — 그 시점에 만든 `docx`와 `pdf`가 남아 있어 실제 스냅샷 역할을 한다. 파일명 정리 이전, 서사 도입 이전의 기획서 원형을 그 파일에서 확인할 수 있다.

**v0.5부터는 변경할 때마다 전체 마크다운 스냅샷을 남긴다.**

## 5. 운영 절차

문서를 수정할 때 다음 순서를 따른다. 사람이 기억하기 위한 것이 아니라 **작업 지시가 없어도 자동으로 지켜지도록** 적어둔 절차다.

| 순서 | 작업 |
|---|---|
| 1 | 수정 **전** 현재 버전 전체를 `백업/v0.N (날짜) 요약/`에 복사 |
| 2 | 문서 수정. **기존 내용은 삭제하지 않는다** — 판단이 바뀌면 원문을 남기고 "개정" 절을 덧붙인다 |
| 3 | 바뀐 수치가 다른 문서에도 있는지 대조하고 함께 고친다 |
| 4 | 각 수정 문서의 머리 표에서 버전을 올리고 개정 이력 행을 추가 |
| 5 | 본 문서 3장 전체 이력에 행 추가 |
| 6 | 검증 스크립트 실행 — `99. 작업 스크립트/검증.py` |

### 검증 스크립트

6단계는 매번 같은 검사를 반복하므로 스크립트로 만들어 두었다. MusicVideo 폴더에서 실행한다.

```
python3 "99. 작업 스크립트/검증.py"
```

| # | 검사 항목 |
|---|---|
| 1 | 마크다운 표의 열 수와 구분선 |
| 2 | 내부 링크가 실제 파일을 가리키는가 |
| 3 | 목차 앵커가 실제 헤딩과 맞는가 |
| 4 | 문서 간 공유 수치가 일치하는가 (사진 253장, 총 기간 28.5일, 비용 상한 등) |
| 5 | 모든 문서의 버전 표기가 같은가 |
| 6 | 최신 스냅샷이 현재 문서와 일치하는가 — 다르면 스냅샷을 안 남긴 것이다 |

공유 수치가 바뀌면 스크립트 상단 `SHARED` 값도 함께 고친다. 6번 검사가 **스냅샷 누락을 자동으로 잡아주므로**, 절차를 잊어도 검증 단계에서 걸린다.

### 기존 내용을 지우지 않는 이유

`02. AI 영상 생성 기술 검증 계획서` 7장이 좋은 예다. 원래 "없던 인물 추가는 권장하지 않는다"고 적었고, 서사 도입으로 결론이 뒤집혔다. 그때 원문을 지우고 새 결론만 남겼다면, 나중에 "왜 이렇게 결정했더라"를 알 수 없게 된다.

원문을 남기고 7.4절에 무엇이 왜 바뀌었는지 적었더니, 오히려 **뒤집힌 게 아니라 원래 안전하다고 본 범주를 확장한 것**임이 드러났다. 변경 이력 자체가 판단의 근거가 된다.

## 6. 되돌리기

| 상황 | 방법 |
|---|---|
| 특정 버전 전체로 | `백업/v0.N .../` 안의 파일을 상위 폴더로 복사 |
| 한 문서만 | 해당 스냅샷에서 그 파일만 꺼낸다. 단 **다른 문서와 수치가 어긋날 수 있으니** 6장 검증을 다시 돌린다 |
| 무엇이 바뀌었는지만 확인 | 본 문서 3장 이력표. 파일 비교가 필요하면 스냅샷과 현재 파일을 대조 |

되돌린 뒤에는 **되돌림 자체를 새 버전으로 기록한다.** v0.5에서 v0.4로 돌아갔다면 그것은 v0.4가 아니라 v0.6이다. 이력이 앞으로만 흐르게 두는 편이 나중에 헷갈리지 않는다.
