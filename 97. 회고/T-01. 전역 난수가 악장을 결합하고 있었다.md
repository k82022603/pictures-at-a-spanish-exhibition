## 1. 증상

4악장과 6악장의 베이스만 고쳤다. 다른 악장은 한 줄도 건드리지 않았다. 그런데 렌더하고 재보니 **손대지 않은 악장들의 숫자가 전부 달라져 있었다.**

| 악장 | 손댔나 | 조성 밖 음 합 (기준선 → 변경 후) |
|---|---|---|
| 5 변주 II | **아니오** | 0.138 → **0.110** |
| 7 그라나다 | **아니오** | 0.132 → **0.143** |
| 9 대문 | **아니오** | 0.087 → 0.096 |
| **9:26 F♯** | **아니오** | **0.119 → 0.124** |

마지막 줄이 문제였다. **9:26의 F♯ 비중은 WBS 1.4.8의 수락 조건**이다. 이 곡의 결론이 걸린 3초이고, 그 값이 아무 음악적 이유 없이 움직였다.

## 2. 원인

`전곡화성.py`에 연주를 사람처럼 들리게 하는 함수가 있다.

```python
RNG = np.random.default_rng(20260805)        # 곡 전체에 하나

def H(t, vel, tj=0.010, vj=0.11):
    return (t + RNG.normal(0, tj),           # 박자를 조금 흔든다
            vel * (1 + RNG.normal(0, vj)))   # 세기를 조금 흔든다
```

`RNG`는 **모듈 전역에 하나**뿐이고, `H()`가 호출될 때마다 난수를 **순서대로 꺼내 쓴다.** 즉 난수는 곡 전체에 걸친 **한 줄짜리 대기열**이다.

4악장에서 베이스가 짚는 자리를 조건부로 바꾸면서 `H()` 호출이 줄었고, 6악장에서는 26번에서 13번으로 줄었다. **대기열이 그만큼 앞으로 당겨졌다.** 그 뒤에 오는 5·7·8·9악장은 원래 받았어야 할 난수 대신 다른 난수를 받았다. 코드는 그대로인데 흔들림이 전부 달라진 것이다.

```
[0악장][1][2][3][4악장][5][6악장][7][8][9]   ← 난수 대기열 하나
                 ↑              ↑
              여기서 줄이면    여기부터 전부 밀린다
```

**이것은 버그가 아니다.** 처음부터 그렇게 설계됐고, 지금까지는 전곡을 늘 한 번에 만들었으므로 아무 문제가 없었다.

문제가 된 건 **작업 방식이 바뀌었기 때문**이다. WBS 1.4는 악장을 하나씩 다시 쓰는 작업이다. 그 순간부터 이 설계는 "악장 하나를 고치면 뒤 악장 전부가 오염된다"는 결함이 된다. **코드는 그대로인데 요구가 움직여서 멀쩡하던 설계가 결함이 됐다.**

## 3. 어제는 왜 못 봤나

**어제 작업이 원리적으로 이 결함을 드러낼 수 없었기 때문이다.**

어제(2026-08-06)는 BL-24b, 무그 신디사이저의 **필터**를 바꿨다. 필터는 `synth.py`의 `moog()` 안에 있고, **`H()`를 한 번도 부르지 않는다.** 소리의 음색만 바꿀 뿐 난수를 꺼내 쓰지 않는다.

그래서 어제 렌더에서는 난수 대기열이 **하나도 밀리지 않았다.** 결합이 존재했지만 작동할 조건이 없었다.

여기에 얄궂은 대목이 하나 있다. 어제 `05` 9.9절은 **"성부 진행 통계가 완전히 같으므로 화성은 안 바뀌었다"**를 근거로 삼았다. 그 추론은 맞았다 — 다만 맞았던 이유가 **"난수가 안 밀렸기 때문"**이었다는 걸 몰랐다. 같은 근거를 오늘 그대로 쓰면 틀린다.

> **어제 못 본 것이 어제의 부주의는 아니다.** 결함이 드러나려면 "한 악장의 음 개수를 바꾸는 작업"이 필요했고, 그건 BL-25가 처음이었다.

다만 **놓칠 뻔한 지점**은 있었다. 오늘도 처음 든 생각은 "내가 5·7·8·9악장을 잘못 건드렸나"였다. 코드를 다시 읽어도 손댄 데가 없어서, 그제서야 "코드 밖에서 악장을 잇는 것이 있다"로 생각이 넘어갔다. **변경하지 않은 곳이 변했으면 원인은 변경한 곳이 아니라 둘을 잇는 무언가에 있다.**

## 4. 어떻게 고쳤나

악장에 들어갈 때마다 난수를 다시 심는다. 대기열을 악장마다 끊는 것이다.

```python
def mark(name, t, seed=None):
    MARK.append((name, t))
    if seed is not None:
        global RNG
        RNG = np.random.default_rng(seed)
```

각 악장 진입 지점에 씨앗을 준다.

| 악장 | 씨앗 | 비고 |
|---|---|---|
| 0 | `20260805` | **전역 초기값과 같다** — 이전 렌더와 그대로 이어진다 |
| 1~9 | `20260806` ~ `20260814` | 악장 번호 + 20260805 |

이제 6악장을 고쳐도 7악장은 자기 씨앗에서 시작하므로 **아무 영향이 없다.**

## 5. 대가

**1~9악장의 흔들림이 한 번 전부 달라졌다.** 되돌릴 수 없는 일회성 이동이다.

| 지표 | 기준선 | 끊은 뒤 |
|---|---|---|
| 경직됨 | 0.941 | 0.955 |
| 9:26 F♯ | 0.119 | 0.136 |
| 3악장 조성 밖 음 | 0.092 | 0.107 |

그럼에도 오늘 치른 이유는 하나다. **작곡이 시작된 뒤에 끊으면 작곡의 변화와 난수의 변화가 섞여서 구별할 수 없다.** 1.4 착수 직전이 마지막 기회였다.

이건 어제 무그를, 오늘 베이스를 1.4보다 먼저 한 것과 같은 논리다 — **중심이 정해지기 전에 주변을 짜면 다시 짠다.** 오늘 그 "중심"에 난수 구조가 하나 더 있었다는 걸 알게 됐다.

## 6. 남은 문제 — 이 발견이 드러낸 더 큰 것

씨앗만 바꿨을 뿐인데 9:26 F♯이 이렇게 읽혔다.

```
0.119   (전역 난수, BL-25 전 코드)
0.124   (전역 난수, BL-25 후 코드)
0.136   (악장별 난수, BL-25 후 코드)
        폭 0.017
```

그런데 **1.4.8 수락 조건은 `≥ 0.135`이고, 기준값(0.135)과 새 필터 값(0.119)의 차이는 0.016이다.**

**재려는 차이보다 측정 자체의 흔들림이 더 크다.** 오늘 최종본이 0.136으로 조건을 넘긴 것도 무그를 손봐서가 아니라 씨앗이 바뀌어서다. 이대로 두면 **씨앗 운으로 통과 여부가 갈린다.**

→ **BL-27**로 올렸다. 씨앗을 여러 개 돌려 분포를 보거나 분석 구간을 늘리는 쪽이 낫다.

그리고 더 넓은 걱정 — **`05` 9장의 다른 실측값들도 같은 문제를 갖고 있지 않은가.** 3악장 조성 밖 음이 0.092인지 0.107인지가 오늘 씨앗 하나로 갈렸다. 통과 기준으로 쓰는 값들의 **재현 폭을 아직 아무도 재본 적이 없다.**

## 7. 재발 방지

- **악장별 난수 격리** — 구현 완료
- **회귀 검사 전에 "무엇이 변해야 하고 무엇이 변하면 안 되는가"를 먼저 적는다.** 오늘은 성부 진행 다섯 지표가 불변이어야 했고 RMS는 움직여야 했다. 그 기대가 없으면 "숫자가 달라졌다"를 해석할 수 없다
- **실측값을 새로 적을 때 재현 폭을 함께 잰다.** 소수점 세 자리를 적으려면 세 자리만큼 안다는 근거가 있어야 한다
- **전역 상태를 순서대로 소비하는 구조를 의심한다.** 캐시·카운터·로그 리스트(`CHORDLOG`)도 같은 성질을 갖는다
