# 세션로그

**이 체계의 원본이다.** 데일리보고와 바이브로그는 여기서 뽑아낸다. 세션로그를 건너뛰면 하루 끝에 기억으로 복원해야 하고, 그때 숫자가 틀린다.

수시로 남긴다 — 하루에 한 번일 수도, 다섯 번일 수도 있다.

## 언제 남기나

- 렌더·검증처럼 **숫자가 나온** 작업을 끝냈을 때
- 문서 버전을 올렸을 때
- 판단이 필요한 지점에서 **검수자 답을 받았을 때**
- 막혀서 방향을 바꿀 때
- 세션이 길어져 맥락이 날아갈 것 같을 때

## 어디에 쓰나

```
98. 일일 마감/YYYYMMDD-HHMM-session-log.md
```

`HHMM`은 **세션을 마치는 시각**이다. 서버 날짜·시각을 실제로 확인해서 쓴다. 추측하지 않는다.

```bash
date "+%Y%m%d-%H%M"
```

**세션로그는 갱신하지 않는다. 매번 새 파일을 만든다.** 데일리보고·바이브로그와 다른 점이다.

이유는 이 문서가 **그 시점의 앎**을 보존하기 때문이다. 오후에 틀렸다고 판명된 것을 오전 로그에서 고쳐버리면, "왜 그때 그렇게 판단했는가"가 사라진다. 오늘만 해도 15시의 "3.8 dB 보정하면 된다"가 16시에 "압축 때문에 2.6 dB만 나온다"로 뒤집혔다 — **두 기록이 다 남아야 다음에 같은 함정을 본다.**

앞 로그가 틀렸으면 새 로그에 `앞서 HH:MM 로그의 X는 틀렸다 — 이유`라고 적는다. 앞 파일은 건드리지 않는다.

## 무엇을 쓰나

**사실과 숫자만.** 판단·소회·반성은 [바이브로그](../vibe-log/SKILL.md)로 보낸다. 섞으면 나중에 사실을 찾을 때 서술을 헤집어야 한다.

### 뼈대

```markdown
# 세션로그 YYYY-MM-DD HH:MM

**프로젝트 버전 — vX.Y → vX.Z**   (안 바뀌었으면 "버전 변동 없음")

## 무엇을 했나

## 실측

## 산출

## 이어서 할 때 알아야 할 것
```

### 각 절에 들어갈 것

| 절 | 내용 |
|---|---|
| **무엇을 했나** | 작업 단위로. WBS 번호나 BL 번호가 있으면 함께 |
| **실측** | 표로. **기준값과 나란히** 놓는다 — "0.941" 이 아니라 "0.941 (v1.5도 0.941)" |
| **산출** | 새로 생긴 파일, 스냅샷 폴더, 렌더한 음원 |
| **이어서 할 때 알아야 할 것** | **가장 중요하다.** 아래 참조 |

### "이어서 할 때 알아야 할 것"

다음 세션이 **모르면 사고 나는 것**을 적는다. 대화 맥락은 세션 사이에 이어지지 않는다.

여기 들어갈 전형적인 것들:

- 작업본과 납품물이 어긋난 상태 (예: `전곡화성.wav`는 새 필터인데 mp3는 옛 필터)
- 임시로 바꿔둔 코드, 백업해둔 파일
- 아직 곡에 반영 안 된 기능 (예: `scream`은 기본값 0이고 아무도 안 넘긴다)
- 쓸 때 지켜야 할 제약 (예: 자기발진 시 컷오프가 곧 음높이라 음집합이 깨질 수 있다)
- 막힌 것과 그 이유 (예: ffmpeg 없어서 mp3 재생성 불가)

## 지킬 것

**실측값은 기준값과 나란히 쓴다.** 이 프로젝트는 "좋아졌다"가 아니라 "1.185 → 0.941"로 말한다. 기준값 없는 숫자는 나중에 비교가 안 돼 쓸모가 없다.

**틀린 것도 그대로 적는다.** 중간에 틀렸다가 고친 과정이 나중에 같은 실수를 막는다. "음정 오차 34센트 → 138센트(틀린 풀이) → 3.9센트"처럼 경로를 남긴다.

**추정과 실측을 구분해서 표기한다.** "약 30초 예상" 과 "8.5초 실측" 은 다른 값이다.

**긴 렌더는 몇 회 돌렸는지 센다.** 나중에 일정 산정의 근거가 된다.

## 하지 말 것

- 판단·소회를 섞기 (바이브로그로)
- 검수자에게 할 요청을 여기 적기 (데일리보고로)
- 기준값 없는 숫자
- 하루치를 파일 하나에 몰아 쓰기
- 프로젝트 버전을 매기거나 `백업/` 스냅샷에 넣기 — **일일 마감 문서는 프로젝트 버전 체계 밖이다.** 명세가 아니라 일지다. `검증.py`도 이 폴더를 보지 않는다
