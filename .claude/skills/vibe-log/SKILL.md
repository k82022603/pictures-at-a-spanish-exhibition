# 바이브로그

**매일 하나.** 세션로그가 "무엇을 했나"라면 바이브로그는 **"어떻게 그렇게 됐나"**다.

이 기록의 값은 이미 증명됐다. `08. 중간 점검과 인수인계`의 "판단이 바뀐 다섯 번"과 "내가 반복한 실수"가 정확히 이런 관찰을 모아 쓴 것이고, 그 덕에 Cowork → Claude Code 인수인계가 **대화 맥락이 하나도 안 넘어갔는데도 거의 공짜**였다.

## 파일 경로

```
98. 일일 마감/YYYYMMDD-vibe-log.md
```

폴더는 평평하게 둔다. `YYYYMMDD-` 접두사가 곧 정렬 순서이고, 이 프로젝트는 총 30 작업일이라 연·월 계층이 오히려 탐색을 늘린다. **파일이 200개를 넘으면** 그때 `98. 일일 마감/YYYY-MM/`로 나눈다.

## 0. 시각을 실제로 확인한다

추측하지 않는다.

```bash
date "+%Y-%m-%d %H:%M"
```

## 1. 모드 판정 — 파일이 이미 있는가

```bash
ls "98. 일일 마감/$(date +%Y%m%d)-vibe-log.md" 2>/dev/null
```

### 있으면 — 갱신 모드

**기존 내용을 지우지 않는다.** 프로젝트 규칙 R3가 여기에도 적용된다.

| 절 | 갱신 방법 |
|---|---|
| 오늘의 결 | 결이 바뀌었으면 **원래 문장을 남기고** 아래에 "(HH:MM 시점) …" 으로 덧붙인다 |
| 인사이트 | **번호를 이어서** 추가 (3번까지 있으면 4번부터) |
| 실수의 모양 | 새 실수가 기존 모양에 들어가면 그 모양에 행을 추가. 새 모양이면 모양을 신설 |
| 판단의 경로 | 새 블록 추가 |
| 바뀐 생각 | 새 Before/After 추가 |
| 나중에 해볼 것 · 아직 모르는 것 | 이어서 추가. **해결된 것은 지우지 말고 `✔ 해결 (…)`로 표시** |
| 자문자답 | 새 Q&A 추가 |
| 숫자 | **덮어쓴다** (누적값이므로) |
| 내일 집중할 것 · 한 줄 교훈 | 덮어쓴다 |

갱신할 때 **바뀐 시각을 표시**한다. 하루 안에서도 판단이 움직인 흔적이 남아야 한다.

### 없으면 — 생성 모드

**직전 바이브로그를 먼저 읽는다.**

```bash
ls "98. 일일 마감"/*-vibe-log.md | tail -3
```

읽는 이유는 두 가지다. **"아직 모르는 것"이 오늘 풀렸는지** 확인해야 하고, **어제 실수의 모양이 오늘 또 나왔는지** 봐야 한다. 두 번째가 이 문서의 존재 이유에 가깝다 — 한 번은 실수지만 두 번이면 습관이고, 습관은 규칙으로 막아야 한다.

## 2. 재료 — 오늘 세션로그 전부

```bash
ls "98. 일일 마감/$(date +%Y%m%d)"-*-session-log.md
```

세션로그가 사실을 갖고 있다. 바이브로그는 **그 사실들 사이의 관계**를 쓴다.

## 절별 지침

### 🎭 실수의 모양 — 이 문서의 심장

**개별 실수 나열은 쓸모가 없다.** 다섯 번 틀렸는데 셋이 같은 모양이면 고칠 것은 셋이 아니라 하나다.

2026-08-06이 그 예다. 세 실수가 전부 **"재는 자리와 거는 자리를 안 맞췄다"**였다 — 위상 조건에서 지연 항 누락, 압축기 뒤에서 잰 값을 앞에 적용, 레벨 보정 전 데모 발송. 묶고 나서야 막는 질문 한 줄이 나왔다.

> 이 값을 어디서 쟀는가, 어디에 거는가, 그 사이에 비선형이 있는가.

**억지로 묶지 않는다.** 안 묶이면 따로 적는다. 없는 패턴을 만들면 진짜 패턴이 묻힌다.

### 🤔 아직 모르는 것 — 누적된다

**해결될 때까지 매일 옮겨 적는다.** 이 절이 이 문서에서 유일하게 날짜를 넘어가는 부분이다.

풀리면 지우지 말고 `✔ 해결 (YYYY-MM-DD, 어떻게)`로 표시한다. 무엇이 얼마나 오래 미결이었는지가 그 자체로 정보다.

현재 열려 있는 것 (2026-08-06 기준):
- `05` 문서 v1.5 실측 기록이 재현되지 않는 원인 (사례 3건)
- 6악장 "비움으로 만드는 광활함"이 실제로 성립하는지
- G3 PoC — 2005년 1024×768에 생성 모델이 통하는지

### 📊 숫자 — 이 프로젝트답게

"좋아졌다"가 아니라 "1.185 → 0.941"로 말하는 프로젝트다. 바이브로그도 예외가 아니다. **핵심 실측 변화**에는 그날 움직인 지표를 기준값과 함께 적는다.

### 💬 자문자답

형식이 아니라 도구다. **답이 궁색하면 그게 신호다** — 그 질문은 「아직 모르는 것」으로 옮긴다.

### 순탄한 날

**억지로 반성거리를 만들지 않는다.** 왜 순탄했는지를 쓰는 편이 낫다 — 준비가 돼 있었는지, 범위가 좁았는지, 앞선 결정이 잘 서 있었는지. 잘 굴러간 이유도 신호다.

그런 날은 「실수의 모양」과 「바뀐 생각」을 비우고 `해당 없음`이라고 적는다. **빈 절을 지우지 않는다** — 틀이 매일 같아야 나중에 비교가 된다.

## 지킬 것

**구체적으로 쓴다.** "꼼꼼하지 못했다"가 아니라 "압축기 뒤에서 잰 3.8 dB를 압축기 앞에 걸었다". 추상적인 반성은 다음에 아무것도 막지 못한다.

**자책하지 않는다.** 목적은 뉘우침이 아니라 다음 세션이 같은 함정을 피하는 것이다.

**규칙으로 뽑히면 인용구로 남긴다.** 나중에 스킬이나 `CLAUDE.md`로 승격하기 쉽다.

> 확인하지 않은 것을 확인했다고 적지 않는다. 정황이 아무리 한쪽을 가리켜도.

**세션로그의 사실을 되풀이하지 않는다.** 필요하면 링크한다.

## 하지 말 것

- 실측값 나열 (세션로그로). 「숫자」 절의 요약치는 예외
- 검수자에게 할 요청 (데일리보고로)
- 내용 없는 자기평가
- 빈 절 삭제 — `해당 없음`으로 남긴다
- 프로젝트 버전 매기기 · `백업/` 스냅샷에 넣기 — **일일 마감 문서는 프로젝트 버전 체계 밖이다**
