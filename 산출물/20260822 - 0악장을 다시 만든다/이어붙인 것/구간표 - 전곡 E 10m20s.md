| 근거 | 어느 경계 | 믿을 만한가 |

## 9. 납품 파일 (2026-08-22 추가)

**`납품.py` 가 구웠다. 손으로 안 구웠다.** 굽고 나서 **되돌려 비트 단위로 대조**한다.

| 파일 | 형식 | 크기 | 검사 |
|---|---|---|---|
| `… .wav` | **float32** · 48 kHz | 227.0 MB | 마스터 |
| **`… (32bit).flac`** | **32비트 무손실** | **170.4 MB** | **★ 비트 단위 100% 일치** |
| `… (24bit).flac` | 24비트 무손실 | 120.3 MB | ★ 비트 단위 100% 일치 |
| `… .mp3` | 320 kbps | 23.6 MB | ★ 길이·표본율 유지 |

### ★ 처음에 16비트로 구웠다

**`납품.py` 가 경고를 찍어 발견했다** — *"마스터가 s16 이다. 32비트로 못 간다."*

`꼬리늘리기.py` 의 `쓰기()` 가 **`np.int16` 으로 저장**하고 있었다.

| | |
|---|---|
| Suno 원본 | **16비트** — 그래서 **정보를 깎은 것은 아니다** |
| 문제 | **우리가 더한 것**(잔향 꼬리·크로스페이드)**은 계산이 더 정밀한데 16비트로 양자화됐다.** 꼬리 끝이 **−85 dB** 인데 16비트 잡음 바닥이 **−96 dB** — **여유가 11 dB 뿐**이었다 |
| 그리고 | **어제 만든 전곡 A 는 float 였다.** E 만 16비트면 앞뒤가 안 맞는다 |

**크기가 증거다** — 같은 32비트 FLAC 인데 **16비트 원본에서는 64.4 MB, float 원본에서는 170.4 MB** 다.

> **「무손실 100% 일치」와 「비트가 살아 있다」는 다른 말이다.**
> 16비트 데이터를 32비트 그릇에 정확히 담았으니 **거짓말이 아니었다.**
> **이 프로젝트가 같은 모양을 세 번째 겪었다** — ① `write_wav` 가 마스터만 16비트로(넉 달)
> ② `ffmpeg -sample_fmt s32` 가 24비트로 ③ 여기. **셋 다 도구가 찍어줘서 알았다.**

**16비트판은 [`잘못 만든 것 - 16비트판/`](<잘못 만든 것 - 16비트판/>) 에 남겼다**(R11).

### 「무손실 100% 일치」가 무엇을 뜻하나 (2026-08-22 추가)

**`납품.py` 는 「FLAC 인코딩이 무손실인가」를 본다.** 절차는 —

1. float32 마스터 → **32비트 정수 wav**
2. 정수 wav → FLAC
3. FLAC → 되돌린 wav
4. **② 의 입력과 ③ 을 대조** ← 여기가 「100% 일치」

**1단계(float → 정수)는 검사 대상이 아니고, 검사할 수도 없다** — FLAC 은 정수 형식이므로 그 변환이 불가피하다.

**그 변환에서 나는 차이를 실측했다.**

| | |
|---|---|
| float32 마스터 vs FLAC 을 float 로 되돌린 것 | **−219.1 dB** |
| 최대 차이 | 2.3e-10 (float32 의 최소 단위는 약 1.2e-07) |
| 견줄 것 | 24비트 잡음 바닥 **−144 dB** · 사람 귀의 한계 **−120 dB** 쯤 |

**−219 dB 는 24비트 바닥보다 75 dB 아래다. 들을 수 없다.**

> **이걸 확인하다가 한 번 잘못 진단했다.** 처음에 「잔향의 `fftconvolve` 가 실행마다
> 다른 값을 낸다」고 봤는데, **두 번의 비교가 정확히 같은 값**(−219.1 dB · 다른 표본
> 187415개)이었다. **같다는 것이 곧 재현된다는 뜻**이었다. **`전곡잇기.py` 는 재현된다.**
