# 산출물 — 날짜별 음원·영상

**여기(git)에는 파일이 없다. README만 있다.** 음원은 Drive에 있고, **이 README는 Drive에도 복사된다** — Drive만 열어도 그 음원이 무엇인지 알 수 있어야 하기 때문이다. 정본은 git이므로 **Drive 쪽을 손으로 고치지 않는다.**

파일 실체는 Google Drive에 있다 — [MusicVideo - 스페인 전람회의 그림](https://drive.google.com/drive/folders/1VKkKWI5kTLqeCjlnBL5GTZsc6JbDQHmu)

> **"무엇이 있었는가"는 이 저장소가 알고, "그 파일"은 Drive에 있다.**

---

## 왜 이렇게 가르나

git은 한 번 넣은 바이너리를 **영원히** 기억한다. 매일 22 MB짜리 mp3를 커밋하면 저장소가 한 달에 0.7 GB씩 붇고, 나중에 지워도 이력에서 사라지지 않는다. 검토 영상 한 편(114.6 MB)은 아예 **GitHub의 파일 크기 한도 100 MB를 넘는다.**

Git LFS는 무료 할당이 월 1 GB라 이 프로젝트의 산출 속도를 감당하지 못한다.

## 폴더 이름

```
YYYYMMDD - 그날의 한 마디
```

`98. 일일 마감/`과 같은 **R2 예외**다. 근거도 같다 — **날짜 정렬이 곧 시간 순서**다. 뒤에 한 마디를 붙이는 것은 목록을 훑을 때 날짜만으로는 무엇을 한 날인지 알 수 없기 때문이다.

프로젝트 버전(`v2.4`)이 아니라 **날짜**로 가르는 이유는, 하루에 버전이 열둘 오른 날이 있기 때문이다(2026-08-07). 검수자가 기억하는 단위는 버전이 아니라 **"그날 무엇을 들었는가"**다.

## README에 무엇을 적나

| 칸 | 무엇 |
|---|---|
| 파일 | 이름 그대로 |
| 무엇 | 한 줄. 무엇을 판정하려고 만든 것인가 |
| 검수 | **★ 채택 / 미채택 / 실패 / 기준선 / —** |

그리고 본문에 **왜 그 파일이 그렇게 생겼는지**를 짧게. 실측 숫자는 정본(`05`)을 가리키고 여기 복사하지 않는다.

**미채택된 것도 지우지 않는다.** "무엇과 비교해서 저것을 골랐는가"가 판정의 절반이다.

## 무엇을 반드시 보관하나

렌더는 **비트 단위로 재현된다**(BL-30). 그래서 자체 합성 음원은 원리적으로 "다시 만들 수 있는 것"이다 — **코드가 남아 있을 때만.**

| | 보관 | 왜 |
|---|---|---|
| **검수 판정 대상** | **반드시** | "무엇을 듣고 승인했는가"의 물증 |
| **외부 도구 생성물** (BL-28 보컬) | **반드시** | 자체 합성과 달리 **원리적으로 재현 불가.** `CLAUDE.md` 6절이 못박았다 |
| 실험·데모 | 하는 편이 낫다 | 다시 만들려면 그때 설정을 복원해야 한다 |
| 중간 wav · 스템 | 안 한다 | 코드를 돌리면 다시 생긴다 |

**2026-08-08 이전 산출물은 코드가 없어 다시 만들 수 없다.** 각 날짜 README 머리에 적어 두었다.

## 언제 쓰나

**파일을 만드는 그 자리에서 한 줄 적고, 마감 때 정리한다.**

마감은 검수자가 말했을 때만 돌므로(R8), 마감 때만 쓰기로 하면 마감이 안 온 날의 파일이 정체 불명이 된다. `daily-closing`이 이 폴더를 훑어 빠진 README를 채운다.
